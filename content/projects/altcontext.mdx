An editor adds a photograph of the founder to a company website. An image model might describe “a person in a red jacket.” The caption supplies a name, but that name could belong to someone mentioned in the article rather than the person in the picture.

AltContext uses the image and the information WordPress holds around it to draft alt text. It checks proposed names against people the site has confirmed, then puts the description in a queue for an editor to accept, change, or reject.

I designed and built the product to make that review practical across a media library. The work is still in development, before public release. The [AltContext site](https://altcontext.com) offers early-access signup.

## Start with the image in its page

Alt text gives people a text alternative when they cannot see an image. What it needs to convey depends on why the image is there. A photograph used to identify the founder has a different purpose from the same photograph used to show a jacket. The [W3C image guidance](https://www.w3.org/WAI/tutorials/images/) explains this relationship between an image and its context.

WordPress already holds clues to that purpose: an image title, caption, filename, and the post around it. AltContext brings those clues into the description request so an editor does not have to re-enter them for every picture.

Those clues can also be misleading. A caption might describe an event without describing anything visible in the photograph. The model is instructed to use the page information as reference material, check it against the picture, and leave out details that conflict with what it sees. Text inside a caption is treated as editorial data, so it is not supposed to become an instruction to the model.

This gives the editor a more informed starting point. It still leaves a judgment to make: does the proposed description serve this image on this page?

## Review a draft before saving it

The review workflow lets an editor inspect generated drafts before applying them to the library. The editor can accept a description or change the wording before saving. Accepting saves the description to the WordPress image; editing saves the editor's version. In this review workflow, generating a draft and applying it are separate actions.

The editor can also mark an image as decorative. That choice is appropriate when the image adds no information that needs a text alternative, such as a purely ornamental flourish. Decorative images use an empty alt attribute, as [W3C recommends](https://www.w3.org/WAI/tutorials/images/decorative/). AltContext keeps that deliberate choice separate from an image still waiting for a description, and does not send decorative images to the model.

The review interface includes a character count and a suggested length of 125 characters. That suggestion does not block saving, and [WCAG does not set that limit](https://www.w3.org/TR/WCAG22/#non-text-content). The editor still has to decide how much wording the image's purpose requires.

An optional mode also saves a longer description alongside the alt text. Keeping these separate gives an editor room for detail without making every image alternative lengthy.

## Check who is in the picture

A person's identity needs more support than a plausible sentence. AltContext maintains a roster of people the site has confirmed. In the People screen, an editor can review the groups of faces associated with each name and correct groups that have been combined or separated incorrectly.

That roster limits which names a description may use. The system checks whether a recognised face supports a proposed name before retaining it in the text. A name supplied only by the caption is meant to be removed.

Recognition can still be wrong. The automated check gives the editor evidence to review; it cannot settle whether the person was identified correctly. A name that passes the check still needs scrutiny in the draft.

## Keep existing work available

Image recognition and description generation run on a hosted service. The plugin sends images for processing, so this product has a different privacy boundary from an app that works entirely on the editor's computer.

If the service becomes unavailable, the plugin cannot produce new results. Saved descriptions and locally stored results remain available.

A separate connection to a third-party model provider was built for evaluation. That connection is disabled by default and requires an explicit opt-in before images are sent through it.

## What the model comparisons showed

Model comparisons tested whether descriptions used the names supplied in the context. Some candidates produced fluent wording but omitted names. Later evaluations showed that smaller models could preserve them too, so model size alone was not a useful way to choose.

These comparisons helped assess a specific behaviour. Including an expected name does not establish that a model can reject a false one, describe unfamiliar images reliably, or produce useful alt text across a whole website.

An early comparison also exposed a more subtle problem. One draft repeated a caption's claim about a research residency, adding background that could not be seen in the photograph. That example led to clearer instructions about describing the image and avoiding unsupported background information.

## What still needs evidence

Automated checks cover the plugin and service, including accessibility checks on the admin interface. The screens were also reviewed against a written inventory of their actions and states, using the [process described here](/research/visual-search-workbench-process/). These checks help catch implementation defects, but they cannot establish whether the descriptions are useful to the people reading them.

A useful evaluation needs to examine both kinds of identity error: keeping a name that does not belong in the picture, and inventing one when none was supplied. A score for including expected names cannot answer either question on its own.

The product also needs evidence from use. Can an editor spot a wrong description, correct a mistaken identity, and understand what will be saved? Do the descriptions give people who rely on alt text the information they need? The model comparisons and automated interface checks do not answer those questions.
