A description such as “a person singing on a stage” can explain an activity while leaving out who is pictured. When the page concerns a particular performer, that identity may be part of the photograph’s meaning.

AltContext is a WordPress product I am designing and building to bring that context into image descriptions. It combines the photograph with identities from a publisher’s named people roster and information from the page. The editor reviews the proposed identity and wording before applying the text. The intended benefit is more useful context for blind readers; the product is still in development.

## Build a description from the photograph, the roster, and the page

The description draws on three inputs with different roles: **the photograph**, **the roster**, and **the page**. Keeping those roles distinct helps explain what supports each part of the proposed text.

**The photograph** supplies visual information about the scene. An image model may describe a microphone, clothing, or the setting. Those observations provide material for the description without requiring the model to identify the person from general knowledge.

**The roster** supplies names the site has established. An editor builds the roster in WordPress by associating groups of faces with people and correcting mistaken groupings. Face matching compares a face in a new image with that site-specific reference. A proposed match still needs review, and the naming policy determines whether a name may be used.

**The page** supplies publishing context, including the image caption and surrounding post. That context helps determine which information matters: a performer’s identity may be important in an event report, while a discussion of a garment may call for attention to the clothing. [W3C’s image guidance](https://www.w3.org/WAI/tutorials/images/) explains how an image’s purpose and context shape its text alternative.

The page cannot establish everything about the photograph. A name mentioned in an article does not, by itself, prove who is pictured. AltContext’s reconciliation step distinguishes information supported by something in the image from context about the page or event, so background information is not simply repeated as though it were visible.

## Review the proposal before applying it

The proposed identity gives the editor a match to inspect. The editor can compare the image with reference photographs and decide whether the person should be named. That decision informs the draft description, whose wording can then be reviewed or changed before it is applied.

The draft and the applied text remain separate. Generating a description does not itself publish it, and a suggested name need not be accepted. The publishing workflow also supports a longer description alongside alt text. An image marked as decorative can skip generation and use an empty text alternative.

## Try the decisions in a practice copy

The guided walkthrough follows the identity decision through to the resulting text. It starts with saved face-match results from a development run. Confirming a match or keeping a person unnamed changes the practice draft; the draft can then be edited, applied to the practice copy, or restored with undo.

The practice copy does not publish to a live page. Its recognition results are saved rather than generated live. An optional live-description path is a separate operation whose availability depends on the service.

[Open the guided walkthrough](https://demo.altcontext.com/wp-admin/admin.php?page=alt-context-dashboard#/guided-prototype). Access is managed through the [AltContext site](https://altcontext.com).

## Connect the interface to the stored decision

My work covers the interaction design and the implementation behind it. The admin interface uses React and TypeScript, the WordPress integration uses PHP, and the supporting recognition and description services use Python/FastAPI. Working across those parts lets me follow an editorial action from its control on screen to the result that is stored.

I use [WorkBay’s UX-map workflow](/projects/workbay/#review-the-interface-as-well-as-the-code) to inventory the interface and produce screens and flows for review. Review findings guide implementation changes, which I check in the running interface. These reviews address structure and behaviour; evaluation with editors and readers has a different job.

## Make the processing and retention choices explicit

AltContext uses a WordPress host and a hosted processing service. WordPress remains the source of record for names, editorial corrections, and saved descriptions. Recognition and description processing run on Oracle Cloud Infrastructure, so images leave the WordPress host for that work. The hosted service stores the recognition representations used to compare faces.

Those hosted records have retention settings, export and purge operations, and controls for withholding names from generated text. Recognition data is retained by default unless another retention mode is selected. Export and purge operations leave an audit trail; purging the recognition data does not remove that trail.

These controls describe the implementation, not a completed legal compliance assessment. They also distinguish AltContext’s hosted processing from on-device processing. Saved descriptions remain in WordPress even when a new service request cannot run.

## Evaluate the description and the review

The evaluation has two audiences: **readers** who use the description and **editors** who review it. Readers need the text to preserve useful context. Editors need to recognise plausible mistakes and correct them before applying the description.

Model comparisons have examined whether supplied identities survive into the text and whether page context introduces unsupported claims. Automated checks cover the plugin and services, including accessibility checks on the admin interface. Those checks address particular behaviours; they do not yet establish the reader benefit or the reliability of editorial correction.

Evaluation with blind readers and editors is therefore still needed. The product’s purpose is to make an image more informative, and those evaluations must establish whether the resulting text achieves that purpose.
