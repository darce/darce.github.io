A coding agent is a language model driving developer tools: it edits files and runs tests, and it reasons inside a context window, the model's short-term working memory, which vanishes when the session ends. What vanishes with it is the working state of a project: which task was active, which review findings are still open, why a decision went one way, and what evidence backs it. WorkBay keeps that state in the repository, so the next session, in any of the supported agent tools, picks the work up where the last one left off.

<PullQuote>
The agent forgets; the repository remembers.
</PullQuote>

## One journey

Work moves through a fixed sequence: a plan becomes a task, the task gets worked, the work gets reviewed, and findings from the review persist until a gate, a recorded check with authority over the branch, decides whether it merges. Every stage writes to one durable record, so the sequence survives any number of session endings along the way.

A cold session loads its active task and continues it. Claude Code, Codex, Cursor, grok, and VS Code Copilot all attach to the same record. Re-entry still carries friction: each tool surfaces the record differently, and context that was never recorded stays lost.

## What the record holds

The record is workflow state: it lives in the project, and a new session reloads recorded decisions directly, with no prose recap. Author and reviewer stay separate, so findings carry their own status and commit provenance while merge authority stays with the parent task. The history is vendor-neutral: one manifest keeps commands consistent across tools, and when a chosen backend is unavailable, dispatch stops and reports the failure.

## A map of the product before the code

WorkBay ships a Design Map tool as the `/ux-map` command. It asks for an inventory first: the jobs a user comes to do, the screens they meet, the zones and states inside each screen, the actions available, and the flows that chain them, each entry carrying a reference into the real code. The inventory lives in one JSON file per surface, checked into the repository like any other source.

The artifacts are there so the screens can be argued about before any of them are built. Reviews cite [the Heuristics Canon](/research/heuristics-canon/), a versioned rulebook whose stable rule IDs make findings checkable later. One critique of [the semantic image search app](/projects/visual-search-workbench/), run by hand against the canon, caught a cancel button wired to a job that could not exist in the state that showed it, filed as a high-severity finding citing the canon rules it broke and the file and line it came from. The repositories that hold maps then guard them like code: tests assert that every label in a wireframe exists in the real interface, and that each screen keeps a single primary action.

## Under the hood

WorkBay stores state in SQLite at `.task-state/handoff.db` and exposes it over MCP, the Model Context Protocol, a standard interface that lets agent tools call external services. Git hooks protect the main branch during development, and a bounded `/offload` command sends a task to an isolated worktree, a separate working copy of the repository, under a fixed token budget, a cap on how much text the model may consume. Optional embeddings add search by meaning over the recorded rows. The memory design has [its own research entry](/research/agent-memory/), the questions agents bring to the record are collected in [a field note from production use](/research/interrogating-agent-memory/), and whether remembering pays for itself is [an open controlled trial](/research/economics-of-agent-memory/).

Installation details and the current schema are in the [WorkBay repository](https://github.com/darce/workbay).
