## The problem

A coding agent starts each session cold. Yesterday's plan, the open review finding, and the reason a change was refused stay behind.

Conversation tools save a summary of the chat. A summary does not carry the open finding, the test that passed, or the decision you must keep.

When that history lives in one agent transcript, the project depends on that agent. Change the tool and the record stays behind.

I moved the record into the repository.

The earlier name for this project was Workstate. The product is now WorkBay. The old URL `/projects/workstate/` redirects here.

## What WorkBay is

WorkBay is a durable agent-state engine for a Git repository. It keeps a local SQLite database at `.task-state/handoff.db`. Agents read and write that database over MCP.

WorkBay records the work:

- the active task, branch, and worktree
- decisions and blockers
- review findings and review runs
- test commands and exit codes
- files that a slice touched

The next agent does not need a long prompt. It asks the project. Claude Code, Codex, Cursor, Grok, and VS Code Copilot read the same rows.

WorkBay stores what the work still owes: what was done, what is still open, and what a merge must refuse. Memory plugins store what was said. WorkBay does not replace them. You can use both.

Paul Klee painted *Highway and Byways* (*Hauptweg und Nebenwege*) in 1929, after a trip to Egypt. The canvas is a field of vertical stripes with one thicker band down the center. I use that painting here because WorkBay keeps the same split. The main path is the task record. The side paths are indexes and generated views. You can delete the side paths and the engine still works.

## How the record works

`handoff.db` is the source of truth. Typed tables hold the state.

| Table | Holds |
| --- | --- |
| `handoff_state` | Active tasks: objective, status, branch, worktree, plan path |
| `decisions` | Decisions with branch, commit SHA, and session |
| `review_findings` | Findings with severity, status, and two commit anchors |
| `review_runs` | Review records with a verdict |
| `verified_tests` | Test commands and exit codes |
| `blockers`, `next_actions` | Open blockers and follow-up work |
| `task_archives` | Snapshots of completed tasks |

`search_handoff` searches those rows with FTS5 and BM25. That is the public search path. Keep it.

Optional embeddings sit on selected concept prose. Cosine rank is for reinjection after a cold start or after compaction. Cosine is not search. Do not move `search_handoff` to embeddings.

`CURRENT_TASK.json` and `DASHBOARD.txt` are generated views. Do not edit them by hand. Regenerate them from the database.

Do not store chain-of-thought or encrypted provider blobs in `handoff.db`. Record typed decisions at the MCP write boundary. Treat provider thought signatures as secrets. Strip them before you index, search, or export.

## How a task moves

A typical task follows this path:

1. Define the scope with `/scope`.
2. Check a draft plan with `/plan-analyze`.
3. Record a formal review with `/planning-review`.
4. Open a branch and a worktree with `make task-start`.
5. Start each slice from a failing test with `/tdd`.
6. Make the tests pass with `/incremental-implementation`.
7. Record a pre-merge review with `/branch-review`.
8. Run the merge gate with `make close-check`.
9. Close and archive with `make task-finish`.

Work lands in small slices. Each slice starts from a failing test. Review findings attach to the branch. High and medium findings must reach zero before `make review-ready` passes. Deferred, wontfix, and superseded are valid exits.

A reviewing agent, usually a different model family, writes findings into the database. The authoring agent reads them on the next `load_session`. Neither agent reads the other transcript.

Git hooks enforce the path while `core.hooksPath` is intact:

- Edits on `main` are refused outside a small allowlist.
- Branch names must match a grammar tied to a task reference.
- `make review-ready` fails while findings are open.
- `make close-check` fails when a slice has no recorded decision.
- Findings and decisions attach to commit SHAs.

An unrestricted shell can still skip hooks. The hooks block the default path. They do not make the repository a sealed box.

For independent work, `/offload` sends one slice to a bounded lane. Each lane owns a worktree and a token budget. The lane never merges. Useful width is the set of ready tasks that do not depend on each other. Those tasks must not touch the same files. The default wave cap is 20. Typical plans use 2 to 6 lanes. Do not raise the cap to force more width.

## How to start

WorkBay installs from tagged refs on [github.com/darce/workbay](https://github.com/darce/workbay). Check the current tag before you install. On 13 August 2026 the current tag was `workbay-v0.3.32`.

Claude Code:

```
/plugin marketplace add darce/workbay
```

Any other agent:

```
REF=workbay-v0.3.32
curl -fsSL "https://raw.githubusercontent.com/darce/workbay/${REF}/scripts/install-workbay-cli.sh" \
  | bash -s -- "$REF"
workbay install --target /path/to/your/repo --remote-ref "$REF"
```

One install does this work:

- writes skill and hook surfaces for Claude Code, Codex, Cursor, Grok, and VS Code Copilot
- registers two MCP servers: `mcp-workbay-handoff` and `mcp-workbay-orchestrator`
- creates `.task-state/handoff.db`
- sets `core.hooksPath`

Restart the agent so it loads the new surfaces. Then run:

```
make context
make task-start TASK=PROJ-1 OBJECTIVE="add rate limiting"
```

If the idea is still vague, start inside the agent with `/scope`.

Use `--no-embeddings` if the repository is new or the host cannot provision the model. Use `/workbay` later to turn embeddings on or off.

After an upgrade, run `workbay doctor --target .`. If the doctor reports drift, run `workbay repair`.

The full install notes live in [`docs/CONSUMER.md`](https://github.com/darce/workbay/blob/main/docs/CONSUMER.md) on the WorkBay repository.

## What to keep small

In August 2026 I checked this architecture against the code and against [heuristics-canon](https://github.com/darce/heuristics-canon). The next work is to keep the engine strict and small. Do not grow a generic memory product.

These rules still hold:

- Keep `search_handoff` on FTS5. Hybrid BM25 plus vector rank exists only as evaluation.
- Do not add a traces table as a second source of truth. Capture typed decisions at the write boundary.
- Do not raise the default wave cap of 20. Measure admitted width against the ready independent set.
- Do not install Superpowers, SkillOpt, or a second skill marketplace. WorkBay already has the ledger, lexical search plus optional embeddings, portable skills, and dependency-aware lanes.
- Strip encrypted provider blobs before they reach search, embeddings, or export.

This is the design test. Remove the concept index and every generated view. If the decisions, scoped FTS5 search, and handoff packets still work, WorkBay is still the engine.

## How I built it

This was backend-heavy work, outside my usual front-end and accessibility base: Python packaging, MCP servers, Git hooks, SQLite migrations, installers, and release automation. I used the same method I use on a UI that must survive an audit. I wrote the spec, split the work, reviewed each slice, and kept the evidence.

Agents wrote a large share of the implementation. I treated that as supervised production. The spec and the architecture stayed with me. I set the acceptance criteria, ran the reviews, and decided when the work was done.

The line back to my accessibility work is short. A remediation claim must survive inspection: the keyboard path, the screen reader behavior, the fix, and the regression test that proves the fix stayed. WorkBay brings that habit to AI-assisted engineering. The agent moves fast. The project keeps the record.
