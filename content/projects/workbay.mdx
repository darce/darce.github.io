The record lives in the repository. Every supported agent reads it. The chat does not own the task.

## What it solves

- Switch agents mid-task. The plan, the open findings, and the tests that passed travel with the work. You can start in Claude Code and continue in Codex, Cursor, Grok, or Copilot. You do not rebuild the thread.
- Use token sales without lock-in. A promotion on one model is a backend change, not a new project. The overhead of a switch is the new login, not a lost history.
- Stay inside the harness you already pay for. WorkBay is native to each agent. You can run Claude inside Claude Code and keep that harness price. You do not need to send the same Claude work through the Anthropic API from another tool.
- Resume half-finished work. Optional semantic embeddings find related decisions and open slices after a cold start, even when the wording changed. The next session can find work that already exists instead of repeating it.
- Keep author and reviewer apart. A second model writes findings the first model must clear. Neither agent reads the other transcript. A merge still needs evidence, not a confident summary.

## How it helps the work

Agentic software work fails in the gaps: after compaction, after a tool change, between plan and patch, between a claim of done and a merge. WorkBay keeps a durable record across those gaps.

A vague idea starts with `/scope`. A draft plan gets a review before anyone opens a branch. Implementation lands in small slices. Each slice starts from a failing test. A different model can review the branch. Open findings block merge. When the task is done, the record archives with it.

The commands are the same in every harness. `/tdd`, `/branch-review`, `/offload`, and the rest mean one thing. Claude Code, Codex, Cursor, Grok, and VS Code Copilot each get a native surface. Bookkeeping runs as make targets, so creating a worktree or closing a slice does not spend a model turn.

`/offload` sends one self-contained slice to a cheaper backend under a token cap. The cheap lane never merges. You review the diff. That is how a studio uses a sale model for mechanical work and keeps a stronger model on the plan and the gate.

Install and the full command list live in the [WorkBay repository](https://github.com/darce/workbay). After install, restart the agent, then start from `/scope` or `make task-start`.

## How I built it

This was backend-heavy work, outside my usual front-end and accessibility base. I used the same method I use on a UI that must survive an audit. I wrote the spec, split the work, reviewed each slice, and kept the evidence.

Agents wrote a large share of the implementation. I treated that as supervised production. The spec and the architecture stayed with me. I set the acceptance criteria, ran the reviews, and decided when the work was done.

The line back to my accessibility work is short. A remediation claim must survive inspection: the keyboard path, the screen reader behavior, the fix, and the regression test that proves the fix stayed. WorkBay brings that habit to an agentic development cycle. The agent moves fast. The project keeps the record.
