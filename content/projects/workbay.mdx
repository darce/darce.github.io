The task record lives in the repository. Claude Code, Codex, Cursor, Grok, and VS Code Copilot all read the same rows.

## What it solves

- Switch agents mid-task. Start in Claude Code. Continue in Codex, Cursor, Grok, or Copilot. The plan, the open findings, and the tests that passed stay on the task.
- Take a token sale when one model is cheap. The switch costs a new login. The history stays in the repository.
- Run Claude inside Claude Code at the harness price. WorkBay installs as a native surface there, so you can keep that work off the Anthropic API.
- Resume half-finished work. Optional semantic embeddings surface related decisions and open slices after a cold start, including when the wording changed.
- Split author and reviewer. A second model writes findings. The first model must clear them before merge. The two agents do not share a transcript.

## How it helps the work

Work breaks after compaction, after a tool change, and between a claim of done and a merge. The task record holds those intervals.

A vague idea starts with `/scope`. A draft plan gets a review before anyone opens a branch. Implementation lands in small slices. Each slice starts from a failing test. A different model can review the branch. Open findings block merge. When the task is done, the record archives with it.

The commands mean the same thing in every harness. `/tdd`, `/branch-review`, and `/offload` keep that meaning wherever you run them. Each agent gets a native surface. Creating a worktree or closing a slice runs as a make target, so that bookkeeping skips a model turn.

`/offload` sends one self-contained slice to a cheaper backend under a token cap. That lane never merges. You review the diff. Mechanical work can go to the sale model. The stronger model stays on the plan and the merge gate.

Install steps and the full command list live in the [WorkBay repository](https://github.com/darce/workbay). After install, restart the agent, then start from `/scope` or `make task-start`.

## How I built it

This was backend-heavy work, outside my usual front-end and accessibility base. I used the same method I use on a UI that must survive an audit. I wrote the spec, split the work, reviewed each slice, and kept the evidence.

Agents wrote a large share of the implementation. I treated that as supervised production. The spec and the architecture stayed with me. I set the acceptance criteria, ran the reviews, and decided when the work was done.

The line back to my accessibility work is short. A remediation claim must survive inspection: the keyboard path, the screen reader behavior, the fix, and the regression test that proves the fix stayed. WorkBay applies that inspection habit to an agentic development cycle.
