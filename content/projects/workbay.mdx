I was leaning on coding agents more, and I kept losing the work around the code.

Claude Code would hold the right context for a branch. Then I'd want Codex for a different pass and rebuild the thread by hand. Summaries helped until I needed the review finding I hadn't fixed yet.

So I moved the record into the repository.

WorkBay is a local SQLite file next to the project. Agents read and write it over MCP. It holds the active task and the review findings still open. It also stores the tests that passed. Claude Code and Codex both hit the same rows. Cursor and Grok do too. So does Copilot.

The short version: the task stays in the repo. You can change the window.

That matters on a Tuesday when Codex is cheap and I already started in Claude Code. I log into the other tool. The history is still there. If I want Claude, I run it inside Claude Code at the subscription price. WorkBay installs there as a native plugin, so I can keep that work off the Anthropic API.

I also got tired of picking up a half-finished slice and watching the next model invent a fresh approach to a decision I'd already made. Optional semantic embeddings help after a cold start. They pull up related decisions and open slices even when the wording changed.

I wanted a second model that could review without reading the first model's pep talk. A reviewing agent writes findings into the database. The author has to clear them before merge. Neither one sees the other transcript.

I think about that the same way I think about a prompt I would ship to a user. What you feed the next model has to earn its way in. A transcript summary is easy to paste. It is also easy for the next agent to treat as fact. WorkBay stores the finding and the commit that backs it.

## How a task actually goes

Start a vague idea with `/scope`. Review the draft plan before anyone opens a branch. Work lands in small slices, each one from a failing test. A different model can review the branch. Open findings block merge. When the task is done, the record archives with it.

The commands mean the same thing wherever you run them. `/tdd` keeps its meaning in every window. So do `/branch-review` and `/offload`. Creating a worktree is a make target, so that bookkeeping does not burn a model turn.

`/offload` is how I send one mechanical slice to a cheaper backend under a token cap. That lane never merges. I look at the diff. The stronger model stays on the plan.

Install and the full command list are in the [WorkBay repository](https://github.com/darce/workbay). Restart the agent after install, then start from `/scope`.

## How I built it

This sat well outside my usual front-end and accessibility work. I spent most of it in Python packaging and Git hooks. The MCP servers and the SQLite schema came with that. I used the same method I use on a UI that has to survive an audit. I wrote the spec first. Then I split the work and reviewed each slice.

Agents wrote a large share of the implementation. I treated that as supervised production. I owned the spec. I set the bar for done and ran the reviews.

I used to treat accessibility claims the same way. If I said a menu was keyboard-accessible, I had to show the path and the regression test. I stay in the loop, and the project keeps the evidence.
