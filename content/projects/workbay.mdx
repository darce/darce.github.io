WorkBay keeps the state of a coding task outside any one AI conversation. It preserves recorded decisions and unfinished review findings so a later session can resume the work, including when I switch between supported coding tools.

I built WorkBay while developing projects such as [AltContext](/projects/altcontext/). A recap could say that a task was nearly finished while leaving out the finding that still blocked it. I needed the next session to retrieve that finding and its evidence, not infer the remaining work from a general account of progress.

## Keep a record the next session can use

Each repository has a SQLite database at `.task-state/handoff.db`. The database holds the task record: what is active, which decisions have been made, what the reviews found, and which checks were run.

The task identifies the current work. Decisions preserve their rationale, while findings retain their severity and resolution status. Test records preserve the commands and results. Together, those records let a later session examine the parts of the work that matter to its next step.

A session loads a selected context packet from the database. That packet brings recorded history into the current conversation without requiring the whole history to be repeated. Optional semantic retrieval supplies another way to find earlier decisions when the current question uses different words.

The retrieved records remain material to inspect. Similarity can suggest that an earlier fix is relevant; it cannot itself close a finding or authorise a merge.

## Resume in another coding tool

WorkBay exposes the same project record to supported tools, including Claude Code, Codex, Cursor, and VS Code Copilot. A session in another tool can retrieve the decisions and findings that the earlier session left behind.

That continuity concerns recorded state. The tools still have different setup requirements and capabilities, and reasoning that was never recorded does not become available simply because the database exists. The record removes one switching cost: reconstructing project history from a conversation held elsewhere.

## Carry a review finding through to a change

An authoring agent can submit work to a reviewing agent without sharing its conversation. The reviewer records findings against the task. Those findings remain available after the review session ends, so the author can retrieve them and address the changes they call for.

A finding’s commit references connect its resolution to the code history. The next reviewer can inspect that history rather than accept a summary saying the problem was fixed. Checks on the normal development path use the recorded state before work is merged.

Git hooks enforce parts of that path while they are installed and configured. They are not a security boundary against an unrestricted shell. WorkBay also supports bounded work in separate working copies, with review and merge authority kept outside the worker.

<h2 id="review-the-interface-as-well-as-the-code">Review the interface as well as the code</h2>

Interface review needs more than a code diff. I use WorkBay’s UX-map workflow to inventory an existing interface or examine a proposed change. The inventory records the screens and their regions, the states each region can show, and the actions and flows that connect them.

That inventory can be rendered as ASCII screens, Mermaid flow diagrams, and Markdown. People and AI tools can review these representations against [Heuristics Canon](/research/heuristics-canon/). The resulting findings can be added to the task record, addressed in the implementation, and checked again after the change.

The workflow separates **validation**, **rendering**, and **critique**. Validation checks whether the map has an acceptable structure. Rendering makes that structure readable in different forms. Critique asks whether particular decisions need attention; it does not implement the answers. A limited automated check pack can also flag issues such as an action pointing to a nonexistent screen.

The public WorkBay repository includes the workflow instructions. The renderer and critique implementation belong to a companion Design Canvas package outside the public mirror. The [VSW interaction reference](/research/visual-search-workbench-screen-reference/) shows how text drawings can accompany an explanation of a product.

## Separate the working tool from its evaluation

WorkBay is in use in my development practice. Its source documents how records persist, how retrieval works, and how the checks use recorded state. That establishes a working mechanism, while its effect on development effort remains a separate question.

The research follows that distinction. [Project Memory Outside the Conversation](/research/agent-memory/) explains the mechanism. [Five Questions I Ask the Project Record](/research/interrogating-agent-memory/) describes its use. [Testing Whether Project Memory Saves Work](/research/economics-of-agent-memory/) sets out the proposed evaluation.
