## Why it exists

Coding agents keep getting cheaper, but never from one vendor at a time. Claude's API is priced for the frontier. Other vendors sell tokens at fire-sale prices to win users, and the cheap capacity moves from month to month. The sensible response is to route each piece of work to whichever model is a good deal this week.

What stops you is that your working context lives inside each vendor's product. The task you were on and the review feedback you have not addressed sit in one transcript, in one app. Switch tools and you start cold, or you paste a summary and hope the next model does not treat a guess as fact.

WorkBay moves that state out of the transcript and into the repository, so the work can follow the price.

## What it is

WorkBay is a small SQLite database in your project, plus the plumbing that lets agents read and write it. It records the active task, the branch it lives on, the review findings still open, and the tests that passed, each tied to a specific commit.

Agents reach the database over MCP, the protocol they already use to call tools. The same commands are generated for Claude Code, Codex, Cursor, grok, and VS Code Copilot from one manifest, so `/branch-review` means the same thing in every harness and feels native in each. End a session in one tool, pick it up in another, and the task continues where it stopped.

| Command | Use when |
| --- | --- |
| `/scope` | The idea is not bounded yet |
| `/tdd` | A slice starts from a failing test |
| `/branch-review` | A branch claims to be done |
| `/offload` | A well-specified slice can go to a cheaper model |
| `/handoff-lifecycle` | You are resuming or switching tasks |

There are fifteen in all. The full list is in the [WorkBay repository](https://github.com/darce/workbay).

## Why you can trust it

A pasted chat summary is a claim. A WorkBay record is anchored to git. When a reviewer flags a problem, the finding carries the commit where it was found and, later, the commit that fixed it. When a test passes, the result is stored with the code it ran against. A second model can review a branch without reading the first model's chat, because everything it needs is already in the database.

Git hooks back this up. Direct edits to `main` are refused. A branch cannot merge while findings are still open. These rules hold no matter which agent is driving, because they run in git, not in the model.

## Cheap tokens, kept at arm's length

`/offload` is the pricing side of the story. It takes a slice of work that is fully specified, sends it to a cheaper backend in an isolated worktree, and caps the tokens it may spend. The result never merges on its own; you review the diff first. A heavily discounted model becomes useful without becoming trusted.

## Embeddings, briefly

Optional semantic embeddings sit on top of the database. Instead of matching exact wording, an agent asks for what matters right now and gets back the open findings, past decisions, and blockers closest in meaning. This has paid off more than I expected, in ways that deserve their own post.

Install instructions are in the [WorkBay repository](https://github.com/darce/workbay). Start from `/scope` and see how far a task travels.
