A later coding session needs more than an account of what happened. It may need the reason an approach was rejected, the finding that remains unresolved, or the test result behind a completion claim. [WorkBay](/projects/workbay/) keeps that material in a project record outside the conversation.

The design has three parts: a **record**, a **retrieval layer**, and a **context packet**. The record preserves decisions and evidence. The retrieval layer finds material that may matter to the current task. The context packet gives the next session a selected portion to read.

These parts describe the mechanism. [The field note](/research/interrogating-agent-memory/) describes how I use it, and [the evaluation proposal](/research/economics-of-agent-memory/) asks whether it reduces work at comparable quality.

## The record preserves decisions and evidence

Each WorkBay repository has a SQLite file at `.task-state/handoff.db`. SQLite stores the database locally without requiring a separate database server. The database contains tasks, decisions, review findings, blockers, and test records.

Those records keep different aspects of the work distinct. A decision has a rationale. A finding has a status and a recorded resolution. A test has a command and result, with task and commit information helping connect the evidence to the work it concerns.

A later session can therefore retrieve a decision as a decision. It need not reconstruct the rationale from a recap saying that planning was completed. The rationale still needs to be checked against present requirements, but the earlier reasoning is available for that check.

## The retrieval layer finds material in the record

Retrieval depends on what the session already knows. A known task or finding can be looked up directly. Known wording can be found through full-text search. A question phrased differently from the earlier record can use optional semantic retrieval.

Semantic retrieval compares numerical representations called **embeddings**. An embedding represents a piece of text as a list of numbers. Comparing these representations can bring related records into view even when their wording differs.

A retrieved record might contain the rationale for an approach rejected earlier. That rationale can explain the original constraint; the constraint can then be compared with the current implementation. The result is a reason to examine the earlier decision, not an instruction to repeat it.

### Keep the index tied to the record

The embeddings form an index over selected fields in the database. Links and text fingerprints connect the index entries to their source records. Those records remain available independently of the index, so the index can be rebuilt without becoming the authoritative version of a decision.

The related-prior-work tool returns candidates for a human or agent to read. Its contract prevents those candidates from automatically closing findings or becoming inputs to a merge decision. Similarity can change which record looks worth inspecting; it cannot establish that two findings are duplicates or that either has been fixed.

The tool also reports why a lookup returns nothing. An empty store, an unavailable provider, incompatible model information, and no result above the threshold are distinct outcomes. In particular, no result above the threshold does not prove the relevant history is absent. The [retrieval implementation](https://github.com/darce/workbay/blob/main/packages/mcp-workbay-handoff/src/workbay_handoff_mcp/embeddings/related_prior_work.py) documents these boundaries.

## The context packet gives the session a selection

A context packet brings selected records into the current conversation. The packet must be bounded because the conversation still has finite space. Loading every past record would compete with the task the session is meant to complete.

The choice of records therefore matters. In an earlier audit of my repositories, review findings accounted for roughly four fifths of embedded entries, with decision rationales making up most of the remainder. That historical distribution describes the material available to retrieve; it is not a target for every project.

The useful question is whether a selected record changes the next decision. A paragraph can sound relevant without supplying the constraint or unresolved finding the session actually needs. That difference between apparent relevance and useful context is one reason retrieval needs evaluation.

## Portability follows the record

The structured record can be exported and read by different supported coding tools. A session in a new tool can retrieve history written by another tool without having its entire conversation. The new tool still needs its own authentication and setup, and its capabilities may differ.

The database stays out of version control by default because it can contain sensitive project material. Keeping the file local does not make every use of its contents private: a context packet sent to a hosted model sends that selected material to the provider. Export and model use both require attention to what the record contains.

## Test what the record changes

The implementation makes recorded history persistent and retrievable. It cannot preserve reasoning that was never recorded or guarantee that each useful record will be found.

Those limits define an evaluation question: when a session receives selected history, does it complete comparable work with less effort? The [economics article](/research/economics-of-agent-memory/) separates the cost of supplying that history from its effect on the result.
