## A session forgets everything

A coding agent works inside a context window: the bounded transcript the model can see at once. Close the session and everything it understood about the project is gone. The next session starts as a stranger.

[WorkBay](/projects/workbay/), an orchestration layer that runs coding agents across repositories and gives them a durable shared record, answers with a database instead of a bigger window. Every repository it manages carries a file called `handoff.db`. It is a SQLite database, which is to say a real database that lives in one ordinary file, with no server to run and nothing exotic required to read it. Sessions write into it the things worth keeping: decisions and the reasons behind them, review findings and how they were fixed, blockers, verified test results. Each write lands as a timestamped row attributed to the session and agent that made it, so the record doubles as an inspectable audit trail of what was concluded and when. The next session starts from a small packet, a bounded selection drawn out of that record, instead of starting cold.

## An index card is not the book

The rows alone would already be memory, but memory you can only search by the words it happens to use. A question that comes back months later is rarely worded the way its answer was written down.

So selected fields are also embedded. An embedding model reads a piece of text and produces a vector: a list of numbers, usually several hundred of them, that works as coordinates. Each number scores the text along one learned dimension of meaning, and together they place the text as a point in a space where nearby points say similar things. Distance between points stands in for distance between meanings, so asking why an approach was rejected lands near the rationale that rejected it, even if that rationale never used the word "reject."

<Diagram

    caption="Meaning becomes coordinates. Distance does the searching."

The vector works like a card in a library catalog: it finds the book, and authority stays with the book. Each card carries a fingerprint of the text it was made from, so a stale card is detectable, and the whole catalog can be reprinted from the rows at any time.

An embedding can find the answer. It cannot be the answer.
</PullQuote>

## Layers of authority

What a session knows arrives in layers. The rows come first: they are the record. When you know the words, exact search answers deterministically, through database queries and plain word search. When you only know the meaning, similarity search over the embeddings proposes candidates. Whatever is found gets cut down to a bounded packet sized to fit at the top of a session, a deliberate spend of scarce context on the task at hand.

<Diagram
    src="/images/research/memory-layers.svg?v=1"
    alt="Four stacked layers narrowing downward: rows as the canonical record, exact search with SQL and full text, meaning search with embeddings, and the packet the next session reads. A small box beside the embeddings layer, annotated 'each vector points back to a row', with an arrow curving up to the rows layer."
    caption="Authority flows downward. Every layer below the rows resolves back to them."
/>

Similarity search has a failure mode exact search lacks: it never returns nothing. It answers "here is the closest thing I have," and as the index grows, the closest thing is always something. So meaning search runs behind hard filters: the index is keyed by record type and task, and the fence is built into the schema, where no query can forget to apply it. Left unfenced, recall degrades into suggestion.

## The record leans toward failure

Across the repositories indexed so far, review findings make up about four fifths of the embedded entries: what broke, and what resolution survived review. Most of the rest are decision rationales. These are the things a fresh session cannot see and would otherwise re-derive. Anyone building their own version can take the bias before taking any of the machinery: index failures and rulings ahead of summaries.

## Private by default, portable on purpose

The record is private by default. `handoff.db` stays out of version control, because the record holds reasoning traces, and reasoning traces hold whatever the agent saw, including whatever secrets crossed its screen. Crossing a machine boundary takes a deliberate, bounded export of chosen rows.

Because the record is plain SQLite, reading it takes only the file and its schema. A harness, the tool that runs the agent, is interchangeable at that layer: Claude Code and Codex both read the same rows today. The record belongs to the repository. That is portable state, and it should not be mistaken for free switching: moving between harnesses still costs authentication, installation, capability gaps, and re-orientation. The durable record removes one cost from that list, the loss of accumulated project history.

## Where the evidence stands

Daily use is testimony, and testimony is the weakest tier of evidence worth naming. That is the ceiling for any description of a running mechanism. The counterexample sits close to home: the youngest database in the fleet holds a few dozen decisions and has no embedding index switched on yet. What agents actually ask a record like this is read out of production data in [a companion field note on the questions agents bring to the record](/research/interrogating-agent-memory/). Whether remembering saves more than it costs is a causal question, and it belongs to [a controlled trial in The Economics of Remembering](/research/economics-of-agent-memory/), where the claim has a criterion it must survive.
