On a fresh launch, an early build of [Visual Search Workbench](/projects/visual-search-workbench/) told the person two things at once: choose a folder, and wait while search prepares. It also offered a Cancel button that could not cancel the preparation.

Each message made sense in isolation. Together, they left the person without a clear next step.

That defect is a useful example of the method behind the app. I used three connected practices: **map the states**, **review the decisions**, and **check the built interface**. This is an account of using them on one product; their value beyond this project still needs testing.

## Map the states

A screen has more to communicate than its successful result. A search screen must also explain an empty library, work in progress, an unreadable file, or a missing drive. Those conditions determine what the person can do next.

Before building the interface, I recorded its screens, regions, states, and connecting journeys in a written **UX map**. For each region, the map described what appears when data is missing, loading, partial, or wrong. This made omissions available for review before they became gaps in the app.

Each screen also had a question to answer. On first launch: how does someone start, and will their photos be copied? During indexing: what does a half-finished collection allow the interface to claim? Those questions gave each review a specific purpose.

The map lived in a version-controlled file. Changes could be compared, and the file could be rendered as simple text drawings for discussion. The drawings helped people inspect the layout while the written map remained the place to update the design.

## Review the decisions

A map records a decision, but it does not establish whether the decision is sound. For that, I used the [Heuristics Canon](/research/heuristics-canon/): a collection of review rules linked to their published sources. A finding could name a rule and explain why it applied, giving me something concrete to accept, challenge, or revise.

Some useful rules came from engineering books. *Designing Data-Intensive Applications* informed how the app treats its search index as a rebuildable copy of information. *Release It!* informed the handling of dependencies that can fail. *Latency* informed the decision to measure slow operations on the target machine.

Those ideas reached the interface through ordinary product questions. If a drive is unplugged, what is missing from the map? If the search model cannot load, what still works? If indexing is unfinished, what does the result count describe?

### Similarity needs an explanation

The search model turns each picture and query into a numerical representation called an **embedding**. The app compares these representations to find nearby candidates. Their usefulness depends on a few constraints that shaped the product.

First, the representations must be comparable. The app uses one defined model and preparation process for its search index and queries. If that definition changes, the index must be rebuilt. The photo files remain the source from which it can be rebuilt.

Second, the nearest pictures are not necessarily good answers. A ranking can return its closest candidates even when none is relevant. The interface therefore avoids confidence percentages. It also warns “No close matches” for a nearly flat ranking while still showing the nearest photos. That check does not establish a reliable relevance threshold for every query.

Third, faster search can introduce its own costs. An approximate search may miss candidates. Measurements on the target machine supported comparing the query with every indexed picture at the tested library size, so that simpler approach shipped. Larger libraries remain an open measurement question.

## Check the built interface

Once the app ran, I checked it against the map again. The [WorkBay](/projects/workbay/) review workflow produced text drawings anchored to the implementation. One drawing exposed the contradictory first-launch state:

The two messages were controlled independently. Both conditions could be true, so both messages appeared. The Cancel button reused an indexing action: pressing it recorded a cancelled indexing job even though no indexing job had started.

A nearby state had a related problem. Search preparation and the Similarity layout could show two almost identical progress bars, each with a Cancel button. Their accessibility names distinguished the jobs, but their visible labels did not.

The fix was to make the status region choose one state at a time. The order gives priority to active work, then errors and instructions, before a request to wait:

<AsciiScreen label="Precedence order for the rebuilt status region, tested top to bottom: indexing shows live work first, then error explains why it stopped, then empty library says what to do, then preparing asks the reader to wait, and otherwise the region reads ready.">

```text
   indexing ───────►  live work first
   error ──────────►  then why it stopped
   empty library ──►  then what to do
   preparing ──────►  then just wait
   otherwise ──────►  ready
```

</AsciiScreen>

The waiting state now names what is loading and offers no Cancel button, because that operation cannot be cancelled:

<AsciiScreen label="The rebuilt waiting state: a single indeterminate bar over the label “Preparing search” and the subtitle “Loading the search model…”, with no Cancel button, because nothing in this state can be cancelled.">

```text
┌────────────────────────────────────────────────────────────────┐
│ ▟▙▟▙▟▙▟▙▟▙▟▙  (indeterminate)                                  │
│ Preparing search   Loading the search model…       (no Cancel) │
└────────────────────────────────────────────────────────────────┘
```

A unit test checks the combinations of inputs and confirms that this region chooses one state, with Cancel available only for indexing. The [screen reference](/research/visual-search-workbench-screen-reference/) records the other release-specific states, including disconnected drives and unavailable models.

The lesson for a product builder is practical: review the combinations as well as the individual messages. A well-written loading message can still be confusing when another region tells the person to do something incompatible.

## Keep the evidence behind a decision

The review process also needed a memory. WorkBay recorded decisions, their rationale, review findings, and the commands used to check changes. A later session could revisit that evidence instead of relying on a summary that said the work was finished.

Recorded findings still needed judgment. Some led to changes; others were withdrawn or superseded. Keeping the reason for each resolution helped prevent later reviews from reopening the same issue without new evidence.

The build tools used search too. Codemap indexed source-code structure, while local text embeddings helped retrieve earlier decisions and findings. Both produced candidates to inspect against the original code or record. A search result alone could not prove that a feature was absent or a decision had never been made.

That is the same constraint the photo interface has to communicate. A view built from part of a collection must explain what it covers. In the app, that explanation helps someone interpret a map. In the build process, it helps a reviewer judge the evidence behind a change.

## What remains to test

This process found concrete defects and led to testable fixes. It has not yet shown how well people outside the reviews understand the resulting interface. A task-based study is the next step: can someone find a useful photo, recognise an incomplete result, and recover when part of the library is unavailable?
