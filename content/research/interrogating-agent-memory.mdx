## The record behind the questions

[WorkBay](/projects/workbay/) gives coding agents a durable project record: the decisions, review verdicts, blockers, and test results of every past session, stored as structured rows that outlive the sessions that wrote them. How the record works has [its own entry](/research/agent-memory/); this note reports what it gets used for.

An agent's working memory is its context window, the bounded transcript it can see at once. Close the session and the window is gone. The questions below recur in real work, and every one of them has its answer outside the window. Everything reported here is read from `handoff.db` files in daily production use. The patterns are measured; the claims about usefulness are testimony from that use, and the two are kept apart on purpose. Because the rows are plain structured data, any agent tool can read what another wrote, so one harness can check another's work without inheriting its transcript.

<PullQuote>
An agent that cannot see a past debate will happily argue both sides of it.
</PullQuote>

## The questions

### Where is the core problem?

Review verdicts accumulate per repository, and their distribution is diagnostic. One small project stood out precisely because of this: roughly three of every four of its recorded reviews failed. A session working there sees one failing review and fixes it in place; the record sees a streak, and in this project the streak pointed at the architecture.

### Has this fix been found before?

The object of this search is a solution that worked. The record indexes accepted fixes, and it is searched by meaning rather than exact wording, so a timeout guard written in March is findable in July as "the retry bug," even though the two phrasings share no words. When a new finding lands, that search runs over past resolutions before anyone re-derives the fix.

### Are we relitigating a settled decision?

The object of this search is a judgment rather than a piece of code. Before an agent re-opens an architectural question, the decision record is searched. "Why is this site static instead of server-rendered?" was settled once, with reasons; an agent that asks again receives the ruling and cites it, and in use the debate stays closed. The failure this guards against is specific to agents: with no memory of the argument, nothing stops a model from being talked back into a position the project already rejected. Human teams have their own version of the failure, and [the Heuristics Canon](/research/heuristics-canon/) is the analogous guard for judgment.

### Is "done" actually done?

A claim of completion checks against rows: verified test results and recorded review verdicts, not the agent's own report. The search by meaning covers the softer half of the question, whether a proposed solution was already discussed, because prior discussion rarely reuses the same words. A different model can re-check the same completion evidence.

### What has already failed?

The object of this search is a dead end. Blockers and abandoned approaches persist past the session that hit them. A recurring failure in agent-assisted development is "let me try a different approach," aimed at an approach that already failed, invisibly, in sessions the current model never saw. The record turns that sentence into a lookup.

## Scope

This note does not show that any of this saves money or tokens. Whether reuse lowers what an agent spends is a causal question, and it is the subject of [a controlled trial in The Economics of Remembering](/research/economics-of-agent-memory/).
