## The claim

Durable memory outside the model reduces the tokens an agent spends to reach the same outcome. This entry registers that claim before measuring it. Everything below is argument, not measurement; the status on this page stays `registered` until the measurement in the last section has been run, and will move to `measured` — or to `closed` with a negative result — when it has.

## The argument

Four mechanisms, in decreasing order of my confidence in them.

**Repeated mistakes are pure token cost.** A mistake an agent cannot see is a mistake it will re-make at full price: the exploration, the wrong fix, the failing review, the retry. The [interrogation note](/research/interrogating-agent-memory/) shows the record holds exactly this class of information — 610 recorded review failures with embedded resolutions. Every one retrieved instead of re-derived is tokens not spent.

**The memory outlives the context window.** Context is a per-session budget; the database is cumulative. Re-establishing project state at the top of every session is a recurring tax that a bounded projection from durable state replaces at a fraction of the size.

**Vendor-agnostic memory is paid for once.** Because the record is SQLite rather than a vendor's proprietary memory feature, every harness reads the same accumulated state. Work done under one vendor's pricing is legible to all of them; switching agents does not forfeit the memory.

**Subsidised seats change where retrieval should happen.** Flat-rate subscription seats are priced below metered API rates for heavy use. The observed anchor: one repository's junior-worker fleet logged 676,751,332 tokens across 323 recorded turns. At metered per-token rates that traffic bills linearly; on a flat seat its marginal price is zero. Memory amplifies the asymmetry — retrieval from the database front-loads context that would otherwise be re-explored as metered traffic.

## What would settle it

The measurement is cheap because the instrumentation already exists: every orchestrated turn writes token counts to a `turn_metrics` table, tagged by task and source.

Design: matched task pairs in the same repository — one arm receives the semantic reinjection packet at session start, the control arm starts cold. Primary metric: total tokens per completed task, from `turn_metrics`, not from estimates. Secondary: count of review-failure repeats already present in the record. Pre-stated success criterion: the claim survives if the memory arm spends at least 20% fewer tokens at an equal or better review pass rate; anything less, and this entry closes negative.

Publishing the design first is the point. The number, when it arrives, will have to live with the criterion written here.
