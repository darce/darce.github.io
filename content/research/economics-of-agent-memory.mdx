## The claim

[WorkBay](/projects/workbay/) hands a new coding-agent session a bounded packet drawn from the project's durable record: prior decisions, review findings, resolutions, blockers, and verified tests. How that record works has [its own entry](/research/agent-memory/); this one is about whether it pays. The claim under test is that starting from the packet lowers the total tokens an agent spends per task while preserving the same outcome quality. Tokens are the metered unit of model work, so tokens per task is the closest thing agent work has to a unit price.

The two halves of that claim are in different states. The packet's price is measured; its effect is not. The distinction matters because a cheap intervention can still hurt: it can distract the agent, or surface stale context that steers the work wrong.

<PullQuote>
The price and the audit trail are known. The effect on an agent's spend is not yet.
</PullQuote>

## The record settles the cost side

I audited three production `handoff.db` databases from different codebases. Each stores its workflow events as structured database rows, which is what makes an after-the-fact audit like this possible at all.

### The packet is a rounding error next to the task

A compact memory packet averages about 300 tokens. The tasks it precedes range from a few thousand tokens to hundreds of millions, and a typical task lands near three hundred thousand: roughly a thousand times the packet that opened it. Whatever else turns out to be true, the direct price of remembering is not the obstacle.

The costs that could still matter are indirect: retrieval latency, stale or irrelevant context, private state leaving its boundary, worse decisions made with misplaced confidence. None of them appears as a line item, which is why the experiment scores the quality of the outcome alongside the token count.

### The shelves are stocked

For memory to save anything, the record has to hold answers worth retrieving, and it does. Across the three codebases, about 99% of findings marked resolved carry a written resolution a later session could reuse instead of re-deriving; no codebase fell below 97%. The record also holds findings that recur across tasks and findings reopened after being closed, and session starts repeat the same orientation queries. All of it is work that has visibly been paid for more than once.

What this settles is the write path: the library is stocked and the shelving is consistent. Whether an agent pulls the right volume at the right moment, and whether that changes what it spends, is the part production history cannot certify.

### Portability pays out now

The same record carries rows written by several different agent tools, and any of them can read the decisions and review evidence the others left behind. For a technologist weighing adoption, this is the return that waits on no experiment: an audit trail and portable project state are worth having even if the token savings turn out small.

## The record cannot settle the benefit

Production history cannot say whether the packet causes savings. Every interactive session receives a packet, so there is no untreated group to compare against. The sessions that meter token spend reliably are the orchestrated worker lanes, and those never receive packets. One instrument has the treatment, the other has the meter, and no session has both.

More mining cannot close that gap. The comparison has to be built on purpose, which is what the experiment is for.

## The experiment

Instrumentation comes first. The interactive harness has to record one audited token total per assigned task. The rule that selects and formats the packet has to be versioned and frozen. Each task's type and expected size has to be recorded before assignment, both arms have to start from the same base commit under the same limits, and a reviewer who cannot see which arm produced the work scores it against a fixed rubric.

<Diagram
    src="/images/research/econ-design.svg?v=3"
    alt="Four stages in sequence. A/A pairs measure pair noise and set the sample size. A content probe compares a relevant packet with an unrelated one. The paired trial randomizes memory against cold starts. The readout reports a token effect interval alongside blinded quality."
    caption="Calibrate the instrument, test whether content matters, then run the paired trial."
/>

Then the run:

1. **A/A calibration.** Pairs of identical cold runs establish how much two attempts at the same task differ on their own. That baseline noise sets how many pairs the trial needs.
2. **Content probe.** A relevant packet runs against an equal-size packet from an unrelated project. If relevance is not even detectable, the trial is not ready.
3. **Matched pairs.** Each task runs twice from the same starting commit, one run with the frozen packet and one cold, assigned at random. Fixed token and time bounds keep either side from running away, and neither run writes back to the shared record until its pair closes.
4. **Readout.** The primary metric is total tokens per task, reported as a confidence interval on the paired difference alongside the blinded quality scores. Failed tasks stay in the denominator.

The success bar is set before the first pair runs: the packet has to cut token spend by at least a fifth, at quality no worse than the cold arm. Fixing the bar in advance is what keeps the eventual result honest, because a threshold chosen after seeing the data can always be argued into place. A fifth is where the saving justifies engineering attention. If the measured interval clears it, the claim stands; if it falls short, the claim closes and the packet keeps its job as an audit trail only. The trial covers one repository's workload, so anything broader would need replication.

The stance going in comes from the [Heuristics Canon](/research/heuristics-canon/) epistemics rule [EXP-01](https://github.com/darce/heuristics-canon/blob/main/lexicons/epistemics.md#exp-01): `require a controlled evaluation and a prior that most ideas are flat or negative`. Most interventions of this shape do nothing. The audit above justifies running the experiment; it does not justify predicting its result.

## The decision in the meantime

A technologist deciding today whether a persistent memory system earns its keep has settled facts and one open question. The direct cost is negligible against the work it precedes. The audit trail and portability across agent tools pay out from the first week. The material worth reusing demonstrably exists. What stays open until the trial reports is whether reuse lowers spend at equal quality.

My own position is cheap insurance: the packet stays on while the instrumentation lands, since its measured price is small and its side benefits are already real. The controlled comparison decides whether it is also making the work cheaper.
