WorkBay: Workflow State for Coding Agents

Open-source developer tooling — github.com/darce/workbay

Why I built it

I regularly move coding work between Claude Code, Codex, Cursor, grok, and Copilot. Git carries the code between them, but it does not carry much of the working state around the code: what I am trying to do, which review findings remain open, why I made a decision, or which test result supported it.

That information usually ends up in a conversation transcript or a generated summary. When I change tools, I either bring the summary with me or reconstruct the task from the repository.

I built WorkBay to keep the narrower, operational part of that context in the repository itself.

What it records

WorkBay creates a SQLite database at .task-state/handoff.db. It records the active task, branch and worktree, implementation decisions, review findings, test evidence, touched files, and the commits associated with them.

Agents access the same state through MCP. I generate the harness-specific command and skill surfaces from one manifest, so the workflow is substantially the same whether I open the repository in Claude Code, Codex, Cursor, grok, or VS Code Copilot.

For example:

CommandWhat I use it for
/scopeTurning an idea into a bounded task
/tddStarting an implementation slice from a failing test
/branch-reviewReviewing a branch and recording findings
/offloadSending a well-specified slice to another backend
/handoff-lifecycleResuming, switching, or closing a task

There are fifteen commands in the current system. The repository documents the complete set.

Moving a task between agents

When I open the same project in another supported harness, WorkBay can load the active task and the state attached to it. Open findings remain open. Recorded decisions remain attached to the task. Test evidence and commit references still point at the code they came from.

This does not make the harnesses interchangeable. Authentication, available tools, model behaviour, shell access, and supported features still differ. I may still need to explain unfamiliar code or provide evidence that was never recorded.

What I avoid is rebuilding the basic workflow state by hand every time I change sessions.

The same mechanism also helps after a long session has been compacted. WorkBay can reload the current task from the database instead of depending entirely on another prose summary of the earlier conversation.

Review state tied to Git

I wanted review findings to survive the reviewer that produced them.

A finding in WorkBay has a status and commit provenance. A later session can see that the finding remains open, which commit addressed it, and whether the branch has reached the state required by the close gate.

The installation also configures Git hooks and Make targets for the workflow I use. They cover things such as edits on main, branch naming, unresolved review findings, and implementation slices that have not reached a recorded disposition.

These hooks are workflow controls, not a security boundary. A process with unrestricted shell access can alter core.hooksPath, skip some hooks, or use the documented bypass mechanisms. Their purpose is to make the normal path consistent across harnesses and sessions.

Running bounded work elsewhere

I added /offload for implementation work that is already well specified.

It gives one slice to an explicitly selected backend in an isolated worktree, with a token budget and a structured result. The worker can commit its work and return a handoff, but it does not merge the result. I inspect the diff or send it through another review pass first.

I use this for mechanical or well-bounded work where using the same model for every step would be unnecessary. Ambiguous design work, architecture decisions, and tasks that depend heavily on evidence from the current session are poor candidates for this kind of handoff.

WorkBay also refuses to silently substitute a different backend when the requested one is unavailable. I would rather have the dispatch fail than change the execution environment without saying so.

Optional semantic retrieval

The SQLite schema is structured, but exact keyword matching becomes less useful as a project accumulates decisions and findings.

WorkBay can optionally embed those database rows and use semantic retrieval when loading a session. The indexed material is still the workflow record: decisions, findings, tests, blockers, and related state. It is not a second transcript store.

I find this most useful on work that spans many sessions. On a new repository with little history, there is correspondingly little to retrieve, and embeddings can be disabled.

Where I draw the boundary

I treat WorkBay as repository-level workflow plumbing.

It preserves selected state that I want another coding session to be able to inspect. It does not preserve the complete reasoning of a previous model, compensate for differences between models, decide what should be built next, or prevent a sufficiently privileged process from bypassing its Git controls.

Its useful unit is something I can make concrete: a task, a branch, a decision, a review finding, a test result, a touched file, or a commit.

That has been enough to let me change coding environments without making the conversation transcript the only record of what happened.

Installation, the complete command set, and the schema are documented in the WorkBay repository.
